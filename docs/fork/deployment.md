# Развёртывание

Репозиторий публичный. Здесь только общая схема. Адреса, порты, состояние файрвола и прочие подробности конкретного сервера в репозиторий не кладём.

## Схема

Один сервер, docker compose, контейнеры в сетевом режиме хоста.

| Компонент | Образ | Примечание |
|---|---|---|
| Бэкенд | `lasuite/meet-backend` | Образ апстрима, Django + gunicorn |
| Фронтенд | `ghcr.io/pirayt/meet-frontend` | Наш образ, собирается `.github/workflows/build-frontend.yml` при пуше в `main` |
| LiveKit | `livekit/livekit-server` | Медиасервер, конфиг `livekit.yaml` |
| Прокси | `livekit/caddyl4` | Caddy с layer4: TLS и разведение трафика на порту 443 |
| Вход | `authelia/authelia` | OIDC-провайдер для входа организатора |
| Данные | `postgres:15-alpine`, `redis:7-alpine` | |

## Правила

- Версии образов фиксируем тегами (`v1.33.0`, конкретная версия LiveKit), а не `latest`. Иначе случайный `docker compose pull` обновит сервис без миграций и проверки.
- Бэкенд и фронтенд обновляем вместе и одной версии. После обновления бэкенда выполняем `python manage.py migrate`.
- Перед обновлением делаем дамп базы (`pg_dump`) и копию папки с конфигами.
- Перед обновлением читаем `UPGRADE.md` апстрима за все пропущенные версии.

## Обследование сервера

Оба скрипта только читают и не выводят значения секретов. Отчёт перед отправкой стоит просмотреть.

```bash
# общая картина: контейнеры, образы, порты
bash bin/inspect-deployment.sh > meet-report.txt 2>&1
# конфиги Meet и LiveKit с замаскированными секретами, файрвол, место на диске
bash bin/inspect-meet-config.sh /путь/к/папке/compose > meet-config.txt 2>&1
```
